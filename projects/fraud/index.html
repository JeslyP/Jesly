Catching fraud without crying wolf.

Fraud is rare and expensive, so a model that calls everything genuine looks 99.9% accurate and catches nothing. I built a fraud model and judged it the way a fraud team would: on transactions it had never seen, by how much fraud it caught, how many false alarms it raised, and how much money it saved.

The data

The public Kaggle credit card fraud dataset: 284,807 card transactions made by European cardholders over two days, of which only 492 (0.17%) are fraud. Features V1 to V28 are anonymised PCA components, alongside the transaction Time and Amount. I removed 1,081 duplicate rows and added two features: hour of day, because fraud is relatively more common overnight, and log-transformed amount.

Testing it like it's live

A random train/test split would let the model learn from transactions that happen after the ones it is tested on. A real fraud system never gets that advantage, so I split by time instead:

  • Train: the earliest 60% of transactions (170,235, with 342 frauds).
  • Validate: the next 20% (56,745), used only to compare models and pick the alert threshold.
  • Test: the latest 20% (56,746, with 74 frauds), touched once at the very end.

Comparing models

I compared a do-nothing baseline with two models, each weighted so the rare fraud cases count as much as the genuine ones. Results on the validation period, at a default 0.5 threshold:

ModelAccuracyRecallPrecisionPR-AUC
Baseline (always "genuine")99.9%0%0%0.001
Logistic regression (class-weighted)95.9%89%2%0.760
Gradient boosting (class-weighted)99.7%81%23%0.743

The baseline wins on accuracy while catching no fraud at all, which is exactly why accuracy is the wrong metric here. I used PR-AUC (average precision), which focuses on the rare class, to choose the model, and logistic regression came out narrowly ahead.

Setting the threshold by cost

A model only outputs a score; someone has to decide where to draw the line. A missed fraud costs roughly the transaction amount, while a false alarm costs an analyst review. Assuming €5 per review, I tested thresholds from 0.01 to 0.99 on the validation period and chose the one with the lowest total cost: 0.91.

Results on the unseen test period

MeasureResult
Fraud caught (recall)63 of 74 (85%)
False alarms278 of 56,672 genuine transactions (0.5%)
Precision18.5% of alerts were real fraud
PR-AUC / ROC-AUC0.746 / 0.983
Estimated fraud losses€7,728 with no model, €3,757 with it: a 51% saving

About one alert in five being real fraud sounds low, but with fraud this rare it is a reasonable trade: each review costs far less than the fraud it can stop, and the threshold was chosen to balance exactly that.

Adding behavioural features

The card dataset's features are anonymised, so it can't show the behavioural signals real fraud systems depend on. I repeated the experiment on PaySim, a simulated mobile-money dataset of 6.3 million transactions with real account IDs, and built features from each account's past activity only: how many payments a payee had already received, payments in the last 24 hours, hours since the last one, whether the payee was brand new, the amount compared with the payee's usual, and the hour of day.

PaySim's documentation warns that fraudulent transactions are cancelled, so its balance columns give the answer away. I kept them out of the real models and trained one comparison model with them, to show how badly a leak inflates the score. All models were trained on hours 1 to 281 and tested on hours 354 to 743 (554,082 transactions, 4,260 frauds).

FeaturesPR-AUCFraud caught when reviewing the top 1% of transactions
Amount and type only0.13817.7%

Behavioural features tripled PR-AUC and nearly tripled the fraud caught within the same review budget. The most useful were hour of day, the amount compared with the payee's usual, how many payments the payee had received before, and whether the payee was new. The near-perfect leaky model is a reminder that a too-good score usually means the model can see something it shouldn't.

Running it as a service

Fraud models aren't built once and handed over, so I packaged the card model as a small production service:

  • Training script that applies the same time-based split and cost-based threshold, and saves the model with a profile of the training data.
  • FastAPI scoring service with /score and /health endpoints, input validation, and a log of every prediction.
  • Drift monitor that compares new data with training data using the Population Stability Index for each feature and for the scores, and checks recall when labels arrive.
  • 13 automated tests run by GitHub Actions on every push, plus a Dockerfile.

It runs on AWS, defined entirely in Terraform and deployed by a one-click GitHub Actions workflow that downloads the data, retrains the model, runs the tests, builds an arm64 container, pushes it to ECR and smoke-tests the live API. Both Lambdas share one container image: one serves the HTTPS API through API Gateway, the other consumes an SQS queue, publishes fraud alerts to SNS, retries only the messages that fail and sends repeat failures to a dead-letter queue. CloudWatch alarms watch errors, p95 latency and the dead-letter queue, and every role has only the permissions it needs. The deployed model reproduced the notebook exactly (85% recall, PR-AUC 0.746).

The first drift check raised a false alarm on hour of day, because any recent window covers different hours from the training period. I excluded that feature from the drift check and documented why, so the monitor only alerts on real change.

What I learned

Pick the metric before the model.

On imbalanced data, accuracy rewards doing nothing. Precision, recall and PR-AUC show what actually matters.

Test the way it will be used.

A time-based split stops the model peeking at the future, so its score is the one most likely to hold up in production.

A threshold is a business decision.

Turning a score into an alert means weighing missed fraud against review costs, so I tied the threshold to money rather than a default 0.5.

Behaviour beats raw fields, and leaks beat everything.

Account history tripled performance on PaySim, but the biggest jump came from columns that leak the label. Reading the data documentation first is what caught it.
