Five minutes to build a university.

Campus Tycoon is a simulation game made in Java with libGDX by a four-person team. You place buildings on a map of York, react to random events, and try to keep student satisfaction high before the clock runs out.

The game

A 300-second timer starts as soon as you begin. Accommodation, study spaces, cafeterias, restaurants and relaxation buildings each cost money and change student satisfaction. Partway through, a random event fires: a student strike, a donation, or a campus cat. Your satisfaction score when the timer hits zero is your final score, and the best scores are saved to a leaderboard.

How it's built

  • Class hierarchies

    Every building extends a shared Building class and every event extends Event, so adding a new one means one small class, not changes across the codebase.

  • Factory-style creation

    The timer pulls the next event from a shuffled queue and creates the matching Event subclass, keeping event logic out of the game loop.

  • Tile map

    The York map is loaded from a text file into grass, lake and mountain tiles, with placement rules and a movable camera.

  • Persistent leaderboard

    Scores are stored with libGDX Preferences, so they survive between sessions on any desktop OS.

Team and process

We worked in short sprints with tasks tracked in Jira, and I coordinated the four of us so features landed in time for each deliverable. Architecture was planned in PlantUML diagrams kept alongside the code.

Revisiting the code

Looking back at the repository in 2026, I found the unit tests had been written but never actually ran: they lived in the main source folder, so Gradle skipped them and JUnit was being bundled into the game itself. Fixing it properly surfaced a real design problem.

  • Moved the tests to src/test and made JUnit a test-only dependency.
  • The renderer created its OpenGL objects the moment the class loaded, so any code that touched it, even to clear the draw queue, crashed without a window. I made them initialise on first draw.
  • Separated the timer's end-of-game logic from the screen change behind a small hook, so game rules can be tested without graphics.
  • Rewrote the leaderboard test to cover parsing, ranking and high-score updates, and added a GitHub Actions workflow that builds and runs all 9 tests on every push.

What I learned

A green build can be lying.

"Tests pass" meant nothing while zero tests were running. Now I check the test count, not just the colour.

Keep rules apart from rendering.

Game logic that reaches straight into the graphics layer is hard to test. A thin seam between them fixed that.
